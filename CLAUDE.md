# Project: SpecHeads — speculative decoding from scratch

## What we are building

A from-scratch implementation of speculative decoding for a frozen `Qwen/Qwen2.5-1.5B-Instruct` target model, with two trained drafters:

1. **Medusa-style heads:** K extra lightweight decoding heads on the final hidden state, each predicting token t+k. Candidates are verified in a single forward pass using tree attention.
2. **EAGLE-style drafter:** a single transformer decoder layer that autoregressively predicts the target's next hidden feature (from the current feature plus the next token embedding), then maps it through the frozen LM head.

Both are benchmarked against vanilla decoding, and against Hugging Face assisted generation using `Qwen/Qwen2.5-0.5B-Instruct` as a separate draft model (the standard baseline; it shares the tokenizer).

**Research question (the novel part):** how much does drafter speedup degrade under domain shift? Train on chat only, then evaluate on chat, code, and math. Then check whether mixed-domain self-distillation recovers the lost speedup.

This is a portfolio project. The core algorithms must be written by us, not imported. Correctness and honest benchmarking matter more than big numbers.

## Hard rules (never break these)

1. **Never fabricate, estimate, or placeholder a metric.** Every number in the README, tables, and figures must be generated by code from saved result files. Missing results are written as `TBD`.
2. **Losslessness is non-negotiable.** Under greedy decoding, speculative output must be token-identical to vanilla greedy output from the same model and precision. This is tested on every drafter and every tree config. If mismatches appear, stop and investigate before reporting any speedup. fp16 numerics can cause rare legitimate divergences, and if so, you must show evidence (logit gap at the divergence point) rather than assume.
3. **Write core logic ourselves.** Do not use the `medusa`, `eagle`, or similar packages, or copy their code. Reading the papers is fine. HF `assisted_generation` is allowed only as a baseline.
4. **Don't trust memory for library APIs.** transformers' cache classes and attention-mask handling change between versions. Check the installed version and read the relevant source before writing KV cache or attention code.
5. **Stop at every phase gate** with a short summary: what you built, what you verified, open questions. Wait for approval before moving on.
6. **Ask before** adding dependencies not listed here, or changing the benchmark protocol after baselines are recorded.
7. Train and eval prompts must be disjoint. Eval sets are never used for training or for tuning hyperparameters (use a separate val split).
8. No secrets in the repo.

## Environment

- **Local machine:** no GPU. Used for code, CPU unit tests with a tiny model (e.g. `Qwen/Qwen2.5-0.5B-Instruct` or a randomly initialized tiny config), data prep, and analysis.
- **GPU:** Kaggle T4 16GB, about 30 hours a week. Be economical, so smoke-test before every long run.
- **T4 constraints:** Turing architecture, so no native bf16 and no FlashAttention 2. Use fp16 for the frozen target, fp32 master weights for drafter training with AMP, and PyTorch SDPA with explicit masks.
- Kaggle notebooks are thin launchers: install the package, load a YAML config, call one entry point. All logic lives in `src/`.
- Python 3.11. Stack: torch, transformers, datasets, accelerate, numpy, pandas, scipy, matplotlib, wandb, pyyaml, pytest.

## Data

- **Training prompts:** a permissively licensed chat instruction dataset (propose options with licenses in Phase 0), plus code prompts and math prompts for the mixed-domain runs.
- **Self-distillation:** training targets are the frozen target model's own greedy responses to training prompts, not the dataset's reference answers. The drafter learns to predict what this model actually says, and that's what drives acceptance rates.
- **Eval sets (fixed, disjoint from training):** about 80 chat prompts (MT-Bench style), about 80 code prompts (HumanEval style), and about 80 math prompts (GSM8K test), with the same max new tokens across all.
- Record the dataset name, version, license, and hash in `data/manifest.json`.
- Don't cache full hidden states to disk (they're far too large). Compute them on the fly with the frozen target in fp16 under `torch.no_grad()`.

## Phases and gates

### Phase 0: Plan and environment check
Propose datasets (with licenses), eval sets, and drafter hyperparameters (K heads, head architecture, EAGLE layer size), plus a memory budget for training each drafter on a T4 alongside the frozen target. Write `docs/plan.md`. **Gate.**

### Phase 1: Vanilla decoding and benchmark harness
1. Our own greedy and sampling decode loop with manual KV cache management, verified token-identical to `model.generate` greedy output.
2. Benchmark protocol: warmup runs, `torch.cuda.synchronize()` around timing, batch size 1, fixed max new tokens, median and p90 tokens per second over all prompts, with 3 repeats per run. Record GPU name, driver, library versions, and commit hash. Kaggle GPUs are shared and noisy, so always benchmark a vanilla baseline in the same session as each method and report speedup relative to it.
3. Run the HF assisted generation baseline with Qwen2.5-0.5B.

These are the "before" numbers, and the protocol is frozen after this point. **Gate.**

### Phase 2: Self-distillation data
Generate target model responses for training prompts, with resume and checkpointing so Kaggle timeouts don't lose work. Store token ids only. Build chat-only and mixed-domain training sets of equal token count, so the domain comparison is fair. **Gate.**

### Phase 3: Medusa heads
Each head is a residual block (linear + SiLU, with a residual connection) followed by the **frozen, shared** base LM head. Don't duplicate the roughly 150k-vocab LM head per head, since memory matters. Loss is cross-entropy for head k predicting token t+k+1, with decaying per-head weights. Report top-1 and top-5 accuracy per head on the val split. Smoke test first. **Gate.**

### Phase 4: Tree verification (the hard part)
1. Start with a **chain** (top-1 from each head), and get losslessness passing.
2. Then build a **candidate tree** from each head's top-k: static tree structures defined in config, a tree attention mask so each candidate attends only to its ancestors and the prefix, and correct position ids.
3. Verification: one target forward pass over all candidates, then accept the longest candidate path matching the target's greedy choice, plus the target's own bonus token.
4. KV cache: after acceptance, keep only the accepted path's KV entries and discard the rest. This is the most bug-prone step, so write focused tests.
5. Tests: the losslessness test across all eval prompts, mask correctness on tiny hand-built trees, and a CPU test with a tiny model.

**Gate.**

### Phase 5: EAGLE-style drafter
A single decoder layer takes the concatenation of the target's hidden feature at t and the embedding of token t+1, and predicts the feature at t+1. The loss combines feature regression (smooth L1) with cross-entropy through the frozen LM head. Draft autoregressively, reusing Phase 4's tree verification. Losslessness tests must pass. **Gate.**

### Phase 6: Experiments
For vanilla, HF assisted generation, Medusa (chain and tree), and EAGLE:
- Wall-clock speedup vs. vanilla, with tokens per second (median and p90)
- Mean accepted length (tokens produced per target forward pass)
- Per-head or per-depth acceptance rates
- Losslessness pass rate (must be 100% for greedy, or divergences explained)
- Added parameters and peak GPU memory overhead

Experiments to run:
1. **Domain shift:** chat-trained vs. mixed-trained drafters, each evaluated on chat, code, and math.
2. **Tree size sweep:** number of candidates vs. accepted length vs. actual speedup. Show where larger trees stop paying off on a T4.
3. **Sampling (temperature > 0):** implement typical acceptance or rejection-sampling verification only after greedy is solid. Clearly mark it as not lossless in the same sense, if that applies.
4. Bootstrap 95% CIs over prompts for speedup and accepted length.

**Gate.**

### Phase 7: Write-up
Generate the README tables and figures from `results/` only. Explain the method in the README with one diagram of tree attention. Include limitations: T4-specific timings, batch size 1 only, a single target model, and shared-GPU noise. Draft the write-up section for the domain shift finding, whatever the result turns out to be (a null result is still a finding). **Gate: final review.**
